## 已完成内容

- `DocumentCache` 新增 `putMissing`，不存在文档首次回源 MySQL 后写入带 `MISSING` 类型的 JSON，TTL 为 60 秒加 0～15 秒抖动；重复查询得到 `NEGATIVE_HIT`，不再访问 Repository。
- `RedisCacheStore` 只捕获 Spring `DataAccessException`，将 Redis 连接失败、命令超时以及写入失败转换为缓存不可用或 `false`；删除结果显式区分 `DELETED`、`NOT_FOUND` 和 `UNAVAILABLE`，不会把幂等删除不存在 Key 误报为错误。
- `RedisDocumentCache` 对 Jackson 解析异常和语义损坏载荷执行精确 Key 删除并返回 `UNAVAILABLE`。语义校验覆盖 JSON `null`、缺失类型、FOUND ID 不匹配、必需字段缺失和结构不合法的 MISSING。
- `DocumentService` 在 `NEGATIVE_HIT` 时直接保留原有 404 语义，在 `MISS` 或 `UNAVAILABLE` 时以 MySQL 结果为准；缓存读写失败不会把已有 MySQL 成功结果或 404 变成 HTTP 500。
- 新增线程安全 `CacheMetricsRecorder`，按 `document` 和 `userPermissions` 区域记录 `hit`、`negativeHit`、`miss`、`error`、`bypass`；`lookup=hit+negativeHit+miss`，`hitRate=(hit+negativeHit)/lookup`，零分母返回 0。
- 新增 `GET /cache-statistics`，经过 Service 返回两个区域的聚合统计，不包含 Redis Key、缓存值或连接地址。
- `error` 的粒度是“失败的缓存操作”，不是“失败的 HTTP 请求”；一次请求的读取和回填都失败时会增加两次。
- `DocumentRepository`、MyBatis Mapper/XML 和测试内存实现新增文档更新能力，只更新 `deleted=0` 的文档；`PUT /documents/{id}` 成功返回 200，不存在或逻辑删除返回 404，标题和正文沿用中文校验规则。
- 文档创建和更新使用数据库事务，保存成功后发布精确文档 ID 事件；`DocumentCacheEvictionListener` 只在 `AFTER_COMMIT` 删除缓存，事务回滚不删除，Redis 删除失败不反向回滚已提交的 MySQL 数据。
- 新增 `DocumentRebuildLock` 边界：Redis 实现使用 `SET NX` 与 3 秒 TTL 原子抢锁、UUID token 标识持有者、Lua 比较 token 后删除；关闭缓存时使用 NoOp 并立即回源 MySQL。
- 热点 Key 竞争者按 20 毫秒轮询缓存，使用 300 毫秒轮询预算；等待期间命中即返回，预算耗尽后不再发起轮询 GET，Redis 不可用、线程中断或预算耗尽后直接回源 MySQL。单次 Redis I/O 另受 500 毫秒命令超时约束，因此 300 毫秒不是整个 HTTP 请求的严格墙钟上限。

## 关键决定和剩余限制

- MySQL 继续是事实数据源；缓存只位于 Service 与 Redis 适配器边界，Controller 不直接操作 Redis。
- 统计是教学用进程内计数，应用重启清零、多实例不聚合；`lookup` 按缓存读取操作而非 HTTP 请求计数，获锁后二次检查和竞争轮询也会计入，不能直接解释为“避免数据库访问的请求比例”。第 9 周再迁移到 Actuator/Prometheus。
- 独立审查未发现 Critical 问题。合法 JSON 的语义校验问题已修复。
- 第 3 天审查指出的“未来自增 ID 已有 `MISSING` 后创建同 ID 文档”问题已由第 4 天 `AFTER_COMMIT` 精确失效修复，并有真实 MySQL/Redis 回归测试。
- 更新顺序固定为 MySQL 提交后删除缓存，不采用提交前删除。在没有并发旧查询稍后回填的顺序流程中，正常删除后的下一次读取从 MySQL 重建；若 Redis 在删除阶段不可用，或者更早开始的并发查询在删除后回填旧 MySQL 结果，旧正值都可能继续存在到 10～12 分钟 TTL 到期，这是当前方案明确接受的最终一致性窗口。
- 第 4 天独立审查未发现 Critical 或 Important 问题。审查指出 300 毫秒仅是轮询预算、cache-aside 并发旧值回填窗口和操作级命中率口径；已补充截止后不再轮询缓存的回归测试与实现，并同步修正文档，不扩大到后续阶段技术。

## 第 3 天学习问答

- 用户已能正确说明缓存穿透、`error` 不属于正常命中率分母，以及空值 TTL 应明显短于正值 TTL。
- 已纠正击穿与雪崩的边界：击穿是单个热点 Key 失效后并发回源；多个 Key 集中过期或 Redis 整体不可用造成广泛回源才是雪崩，数据库宕机不是缓存雪崩的定义。
- 已纠正布隆过滤器语义：它回答的是“元素一定不存在或可能存在”，不是判断数据是否位于缓存；空值缓存则是在 Redis 保存短 TTL 的不存在标记。
- 已补充异常边界：仅降级预期的 Redis 数据访问异常和 Jackson 编解码/载荷异常；不能吞掉全部 `RuntimeException`，否则会隐藏空指针、参数错误和业务程序缺陷。

## 第 4 天学习问答

- 用户已准确说明锁必须原子设置 TTL，避免加锁后进程崩溃造成永久死锁；也能准确说明旧持有者直接 `DEL` 可能误删新持有者的锁，因此必须用唯一 token 和 Lua 原子比较删除。
- 已补全提交后删除的理由：不仅防止提交前崩溃或回滚造成无意义失效，更关键的是避免删除后、数据库提交前的并发读把旧值重新回填缓存；MySQL 始终是事实来源。
- 已补全最终一致性边界：数据库提交到删除之间可能旧读、Redis 删除可能失败，且更早开始的查询可能在删除后回填旧值；最坏陈旧时间主要由旧缓存剩余 TTL 决定。
- 已补全等待降级理由：有限等待不仅减少延迟，也防止请求线程长期占用和故障放大；预算耗尽后回源 MySQL，保证 Redis 或重建者异常时核心查询仍可用。“饥饿”不是这里最准确的主要描述。
