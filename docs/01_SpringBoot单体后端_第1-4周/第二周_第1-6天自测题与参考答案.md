## 第 1 天：数据库基础、约束与事务

### 应掌握的内容

- 主键、代理键、业务唯一性、联合主键和外键。
- Java 参数校验与数据库约束的职责边界。
- `COMMIT`、`ROLLBACK` 和事务可见性。
- 开发库与测试库隔离以及可重复初始化。

### 自测题与参考答案

#### 1. `已有归档` 为什么用户角色关联表适合使用 `(user_id, role_id)` 联合主键？

这两个字段的组合正好表达一条“用户—角色”授权关系的业务唯一性。单独的 `user_id` 和 `role_id` 都允许重复，但同一组合不能重复。联合主键同时保证两个字段非空并阻止重复授权。

#### 2. `已有归档` 如果关联表使用普通自增主键，还必须增加什么约束？

还必须增加 `UNIQUE (user_id, role_id)`。否则不同的自增 ID 可以保存完全相同的授权关系，代理键唯一并不等于业务关系唯一。

#### 3. `已有归档` 自增代理键和业务字段分别承担什么职责？

自增代理键为记录提供短小、稳定、与业务变化无关的身份；用户名、邮箱、角色编码等业务字段承载业务含义，并通过非空、长度和唯一约束维护业务规则。

#### 4. `已有归档` Java 参数校验和数据库约束各自保护哪一层？

Java 校验位于应用入口，负责必填、格式、长度以及友好的中文错误消息。数据库约束位于最终写入边界，防止并发请求、脚本、其他程序或应用缺陷写入非法数据。两者互补，不能互相替代。

#### 5. `本次补充` 唯一约束和外键分别解决什么问题？

唯一约束防止同一业务身份重复，例如重复邮箱；外键防止子表引用不存在的父表记录，例如给不存在的用户授予角色。前者保证唯一性，后者保证引用完整性。

#### 6. `已有归档` 为什么当前事务能查询到自己刚插入但尚未提交的数据，而其他连接通常看不到？

事务必须能够“读到自己的写入”，否则同一业务动作无法继续处理刚产生的数据。其他连接受事务隔离和一致性视图保护，通常不能读取未提交修改，因此不会发生脏读。

#### 7. `已有归档` `ROLLBACK` 和 `COMMIT` 分别有什么作用？

`ROLLBACK` 撤销当前事务尚未提交的修改；`COMMIT` 确认并持久化本次事务修改。提交后，其他连接能否马上读到新值还取决于它是否仍在使用旧事务快照。

#### 8. `已有归档` 哪些 SQL 应当放进同一个事务？

共同完成一个不可分割业务动作、要求“全部成功或全部失败”的 SQL 应在同一事务中。例如更新工单状态并写入操作记录，如果只成功一半会破坏一致性，就必须组成一个事务。

#### 9. `本次补充` 为什么建议显式命名数据库约束？

显式名称能让报错直接指出违反了哪个业务规则，便于测试断言、问题定位和数据库迁移。例如 `uk_practice_users_email` 比数据库自动生成的名称更稳定、可读。

#### 10. `本次补充` 为什么开发库和测试库必须分开？

集成测试会重复建表、清理和写入数据。独立测试库可以避免清理脚本误删开发数据，也让测试具备可重复性。测试配置还必须显式校验数据库名称，形成额外安全边界。

### 掌握标准

能够独立解释联合主键、代理键、唯一约束、外键、Java 校验、数据库约束和事务提交/回滚的职责，并能说明测试库为什么不能与开发库混用。

## 第 2 天：用户 MyBatis 持久化链路

### 应掌握的内容

- HTTP 请求经过 DTO、Controller、Service、Repository、Mapper 和 MySQL 的完整链路。
- Repository 接口、MyBatis 适配器、Mapper 和 Record 的边界。
- 自增主键回填、参数绑定、逻辑删除和异常转换。
- 单元测试与真实 MySQL 集成测试使用不同 Repository 实现的原因。

### 自测题与参考答案

#### 1. `已有归档` `POST /users` 从请求到响应经过哪些组件？

完整主链路是：`DispatcherServlet → JSON 反序列化和 DTO 校验 → UserController → UserService → UserRepository 接口 → MyBatisUserRepository → UserMapper/UserMapper.xml → MySQL users 表`。返回时再由 Repository 把 Record 转为 `User`，经过 Service、Controller 包装为 `ApiResponse<User>` JSON。

#### 2. `已有归档` 为什么 `UserService` 依赖 `UserRepository`，而不是直接依赖 `UserMapper`？

Service 负责业务用例，只需要“保存用户、按 ID 查询用户”的持久化契约。Mapper 是 MyBatis 实现细节。依赖接口可以让业务层与数据库框架解耦，并允许单元测试换成内存实现。

#### 3. `本次补充` `MyBatisUserRepository` 和 `UserMapper` 分别负责什么？

Repository 是领域持久化适配器，负责异常转换以及 `UserRecord` 与 `User` 之间的映射；Mapper 负责声明数据库操作并与 XML 中的 SQL 对应。Mapper 不应该处理 HTTP 响应或业务异常消息。

#### 4. `本次补充` 为什么要区分 `User` 和 `UserRecord`？

`User` 表达业务领域数据，`UserRecord` 服务于 MyBatis 的可变 Bean 映射和数据库字段。分开后，数据库结构或框架要求不会直接污染领域对象及对外 JSON。

#### 5. `已有归档` MySQL 生成的自增 ID 如何回到 Java 对象？

Mapper XML 使用 `useGeneratedKeys="true"` 和 `keyProperty="id"`。插入完成后，MyBatis 把数据库生成的主键写回传入的 `UserRecord.id`，Repository 再用它构造 `User` 返回。

#### 6. `已有归档` MyBatis 的 `#{}` 和 `${}` 有什么区别？

`#{value}` 使用 JDBC 预编译参数绑定，参数值不会被解析成 SQL 结构，适合用户名、邮箱和 ID 等外部数据。`${value}` 是直接文本替换，外部输入可能改变 SQL 语义并造成 SQL 注入，只能用于经过严格白名单控制的少数 SQL 标识符场景。

#### 7. `已有归档` 为什么不能只通过“先查询是否存在”防止重复用户名或邮箱？

两个并发请求可能同时查询到“不存在”，随后都尝试插入。最终必须由 MySQL 唯一约束原子地决定谁能写入，应用层预查询只能改善提示或减少无效尝试，不能替代唯一约束。

#### 8. `本次补充` 为什么要把 `DuplicateKeyException` 转换成领域异常？

数据库异常可能包含 SQL、表名和驱动细节，不适合作为稳定 API。Repository 在持久化边界将其转换为 `DuplicateResourceException("用户名或邮箱已存在")`，再由全局异常处理器返回 HTTP 409 和稳定错误码。

#### 9. `本次补充` 为什么按 ID 查询必须固定包含 `deleted = 0`？

项目使用逻辑删除，数据仍保留在表中。如果正常查询遗漏该条件，已删除用户会重新进入业务流程。过滤逻辑应固化在 Mapper SQL 中，而不是要求每个调用方记住。

#### 10. `本次补充` 为什么 Service 单元测试仍使用内存 Repository，而 Controller 集成测试使用 MyBatis Repository？

Service 单元测试关注业务行为，内存实现执行快、定位清晰；Controller 集成测试需要验证真实的 HTTP、Spring Bean、Mapper SQL 和 MySQL 链路。两类测试目的不同，组合使用可以兼顾速度和真实性。

### 掌握标准

能够从 `POST /users` 开始完整复述请求和返回链路，并解释 Repository 接口、Mapper、Record、主键回填、参数绑定、唯一约束和异常转换各自解决的问题。

### 自测题与参考答案

> 本日在原练习记录中没有独立自测题；以下题目由本轮问答和实际实现补建。

#### 1. `已有归档` 文档创建请求经过哪些层？

请求链路是：`HTTP → DocumentController → DocumentService → DocumentRepository → MyBatisDocumentRepository → DocumentMapper/DocumentMapper.xml → MySQL`。Controller 管理 HTTP 边界，Service 编排业务，Repository 隐藏持久化实现，Mapper 执行 SQL。

#### 2. `已有归档` 为什么 Service 依赖 Repository 接口而不是 Mapper？

Service 只依赖“保存和查询文档”的业务持久化能力，不需要知道 MyBatis 或 MySQL。这样可替换实现、便于单元测试，也能阻止 SQL 细节进入业务层。

#### 3. `已有归档` 为什么区分 `Document` 和 `DocumentRecord`？

`Document` 表达领域数据，`DocumentRecord` 对应数据库和 MyBatis 映射。Record 可以包含 `createdAt` 等审计字段，而领域对象和 API 不必暴露这些字段。

#### 4. `已有归档` `useGeneratedKeys` 在文档插入中解决了什么问题？

它把 MySQL 生成的自增 ID 回填到 `DocumentRecord.id`，Repository 无需额外查询即可构造带 ID 的领域对象。

#### 5. `本次补充` 为什么查询要显式列出字段，而不是使用 `SELECT *`？

显式字段让 SQL 契约清晰，避免新增数据库列后意外进入映射或对外响应，也减少无用数据读取，并使 Record 与查询结果的对应关系更容易审查。

#### 6. `已有归档` 为什么查询和更新都要考虑 `deleted = 0`？

逻辑删除记录仍在表中。正常查询必须隐藏它，更新也必须防止它被再次修改或“复活”。把条件写入 SQL 可保证所有调用路径遵守相同规则。

#### 7. `本次补充` 为什么要测试超过 1,000 字符的中文、换行正文完整往返？

简单英文短文本无法证明列类型、连接字符集和映射没有截断或乱码。长中文和换行的真实写入—读取测试能同时验证 `utf8mb4`、`LONGTEXT` 与 MyBatis 映射。

#### 8. `本次补充` 为什么标题 200 字符边界要同时由 DTO 和数据库保护？

DTO 在 HTTP 入口提前返回清晰的 400 错误，数据库 `VARCHAR(200)` 是最终数据边界。两者一致可以避免合法边界被误拒绝，也避免超长输入穿透后变成数据库 500。

#### 9. `本次补充` 为什么要从 `InMemoryDocumentRepository` 移除运行时 `@Repository`，但保留这个类？

运行时只能有一个明确的 `DocumentRepository` Bean，因此改由 MyBatis 实现注册；内存实现仍适合快速 Service 单元测试直接构造。这样既完成生产切换，也保留轻量测试能力。

#### 10. `本次补充` 为什么没有立即抽取用户和文档 Repository 的通用基类？

目前只有少量相似的 Record 转换和 Mapper 调用，业务字段和异常规则仍不同。过早抽象会增加间接层和理解成本；应等重复稳定且确实影响维护时再提取。

## 第 4 天：工单事务与并发安全

### 应掌握的内容

- 快照读、当前读、`SELECT ... FOR UPDATE` 和行锁释放时机。
- “加锁读取—状态校验—更新”必须处于同一事务。
- 并发状态流转的竞态条件、锁范围和事务代理。
- 更新影响行数、数据库字段容量与 HTTP 输入校验。

### 自测题与参考答案

#### 1. `已有归档` 普通 `SELECT` 和 `SELECT ... FOR UPDATE` 有什么区别？

普通 `SELECT` 在 InnoDB 默认隔离级别下通常是快照读，不会取得阻止其他事务更新同一行的排他锁。`SELECT ... FOR UPDATE` 是当前读，会读取最新可见数据并锁定命中记录；其他事务更新或再次锁定同一行通常需要等待。

#### 2. `已有归档` `FOR UPDATE` 的锁什么时候释放？

锁在事务提交或回滚时释放，不是在查询方法返回或 SQL 执行结束时释放。若处于自动提交模式，语句结束就提交，后续校验和更新将失去锁保护。

#### 3. `已有归档` 不加锁时，两个并发状态更新为什么可能都成功？

两个事务可能都先读到 `PENDING`，都判断 `PENDING → PROCESSING` 合法，然后依次更新。第二个请求依据的是过期快照，却仍报告成功，这就是“读—校验—写”竞态。

#### 4. `已有归档` 为什么本项目只锁一条目标工单？

一次状态变更只依赖一个工单聚合。按主键锁定目标行即可让同一工单的变更串行化，同时允许不同工单并发处理，减少无关等待和多行锁顺序不一致导致的死锁风险。

#### 5. `已有归档` 为什么 `@Transactional` 要覆盖完整的状态流转方法？

加锁读取、校验和更新必须共享同一事务与数据库连接。如果查询事务先结束，锁会提前释放，后续业务判断仍可能被其他事务穿插。

#### 6. `本次补充` 为什么事务边界放在 Service，而不是 Controller 或 Mapper？

事务应围绕完整业务用例，而 Service 正好负责编排“读取—校验—写入”。Controller 只处理 HTTP，Mapper 只执行单条数据库操作，都看不到完整业务原子性。

#### 7. `已有归档` Spring `@Transactional` 的代理机制有什么常见陷阱？

事务通常由 Spring 代理在 Bean 外部调用时开启。同一个类内部通过 `this.method()` 调用带事务的方法可能绕过代理，使注解不生效。本项目由 Controller 或测试通过 Spring Bean 调用 public `updateStatus`，不存在该自调用路径。

#### 8. `已有归档` 为什么更新后要检查 SQL 影响行数？

按 ID 更新有效工单正常应影响 1 行。0 行可能表示记录不存在或已逻辑删除，超过 1 行说明条件或约束有严重问题。检查行数可以避免把未更新或异常更新静默当成成功。

#### 9. `已有归档` 为什么工单描述要按 UTF-8 字节数校验，而不能只看 Java 字符数？

MySQL `TEXT` 上限约为 65,535 字节，不是固定数量的 Java 字符。英文、中文和 emoji 的 UTF-8 字节数不同；例如许多 emoji 占 4 字节。按字节校验才能在进入数据库前稳定返回 HTTP 400，而不是数据库异常 500。

#### 10. `本次补充` 并发测试为什么必须使用真实 MySQL，而不能只使用内存 Repository 或 Mock？

事务、隔离级别、当前读和行锁都是数据库行为。内存实现和 Mock 无法证明 `FOR UPDATE` 是否真的等待、锁何时释放以及两个连接如何竞争，因此只能用真实 MySQL 得出并发结论。

#### 11. `本次补充` 一个可靠的并发回归测试应断言什么？

两个线程同时把同一工单从 `PENDING` 更新为 `PROCESSING` 时，应只有一个成功，另一个因看到最新 `PROCESSING` 而抛出非法状态流转异常，最终数据库状态为 `PROCESSING`。测试还应有同步点，避免线程完全串行而产生假通过。

#### 12. `本次补充` 数据库默认值、CHECK 约束和 Service 状态机分别承担什么职责？

插入 SQL 或默认值保证初始状态是 `PENDING`；数据库 CHECK 防止任何入口写入枚举之外的非法值；Service 状态机判断当前状态到目标状态是否符合业务顺序。三者保护的层次不同。

### 掌握标准

能够画出并解释：`事务开始 → FOR UPDATE 读取最新状态并锁行 → 校验状态机 → UPDATE 并检查影响行数 → COMMIT/ROLLBACK → 释放锁`，并能说明不加事务、不加锁或扩大锁范围分别会产生什么问题。

## 第 5 天：分页、索引与执行计划

### 应掌握的内容

- 一页式分页参数、offset 计算、稳定排序和摘要 DTO。
- 动态查询中 items SQL 与 count SQL 的一致性。
- B+Tree 联合索引的最左前缀、等值条件、范围条件和排序关系。
- 前缀查询与前导通配符查询的访问路径差异。
- 回表、覆盖索引和 `EXPLAIN ANALYZE` 关键字段。

### 自测题与参考答案

#### 1. 为什么本项目规定 `page` 从 1 开始、`size` 最大为 100，并使用 `long` 计算 offset？

统一从 1 开始可以让 HTTP 契约更直观；限制 `size` 防止一次请求读取过多数据；offset 使用 `(long) (page - 1) * size`，避免先用 `int` 乘法导致溢出。非法参数在 Service 创建 `PageRequest` 时统一转换为 HTTP 400。

#### 2. 为什么分页排序必须写成 `created_at DESC, id DESC`，不能只按创建时间？

多条记录可能拥有完全相同的 `created_at`。只按时间排序时，这些记录的相对顺序没有保证，翻页过程中可能重复或遗漏。唯一 ID 作为第二排序键可以建立确定的全序。

#### 3. 为什么列表响应不返回文档 `content` 或工单 `description`？

列表只需要身份、标题、状态和时间等摘要信息。大文本会增加数据库读取、网络传输和 JSON 序列化成本；因此 Mapper 列表 SQL 不选择大文本列，并使用独立摘要模型和 DTO 从结构上阻止误返回。

#### 4. 为什么 items 查询与 count 查询必须使用完全相同的筛选条件？

`items` 表示当前筛选条件下的一页数据，`total` 必须表示同一结果集的总数。如果两条 SQL 的逻辑删除、状态、前缀或关键字条件不一致，前端就会得到错误的总页数，甚至出现“当前页有数据但 total 为 0”等矛盾。

#### 5. 为什么 `LIMIT`、`OFFSET` 和筛选值仍然使用 `#{}`，而排序字段固定写在 SQL 中？

数值和筛选值都是数据，使用 `#{}` 交给 JDBC 预编译绑定，避免 SQL 注入和类型拼接问题。排序字段属于 SQL 结构，不能把客户端输入直接用 `${}` 拼进去；本项目没有开放自定义排序，而是把稳定排序固定在 Mapper XML。

#### 6. 什么是联合索引的最左前缀？本项目工单查询如何体现？

联合索引按从左到右的列顺序组织。查询通常要先使用最左列，再连续使用后续列，才能有效缩小扫描范围。例如 `(status, deleted, created_at DESC, id DESC)` 适合先按 `status`、`deleted` 等值筛选，再按时间和 ID 倒序读取。无 `status` 条件时，本项目改用另一个以 `deleted` 开头的索引。

#### 7. 等值条件、范围条件和排序列在联合索引中有什么关系？

前导等值条件先确定连续索引区间；随后排序列与索引方向一致时，数据库可以按索引顺序直接读取。遇到范围条件后，再靠更右侧列继续精确定位或满足全局排序通常会受限制。因此索引设计要结合真实的筛选方式与排序，而不是简单把所有列堆在一起。

#### 8. 为什么 `LIKE 'Spring%'` 能使用标题范围，而 `LIKE '%Spring%'` 通常不能？

普通 B+Tree 按字符串从左到右排序。`Spring%` 的开头已知，可以转换为从 `Spring...` 开始的一段连续范围；`%Spring%` 的开头未知，匹配值可能散布在所有标题中，无法用标题有序性直接定位，只能扫描更多候选值后逐条判断。

#### 9. 执行计划显示使用了索引，是否就代表查询已经充分利用该索引？

不代表。本次 `%Spring%` 查询仍显示使用 `idx_documents_deleted_title_id`，但 `key_len=1`，说明主要只利用了第一列 `deleted`；估算要检查 1,140 条有效记录，并出现 `Using filesort`。必须结合 `type`、`key_len`、rows、过滤比例和实际执行树判断使用程度。

#### 10. 什么是回表？什么是覆盖索引？

二级索引找到候选主键后，如果查询还需要索引中没有的列，就要再读取聚簇索引记录，这一步叫回表。如果筛选列和返回列都能从同一个索引取得，就可以只读索引完成查询，称为覆盖索引。本次 `role_permissions` 查询只按 `role_id` 过滤并返回 `permission_id`，联合主键已包含两列，因此显示 `Using index` 和 `Covering index lookup`。

#### 11. 阅读本次 `EXPLAIN ANALYZE` 时应重点看哪些信息？

先看选择的 `key`、访问类型和估算 rows，再看执行树中的 actual time、actual rows、loops，以及是否出现 Sort、Table scan、Index lookup 或 Covering index lookup。估算值用于理解优化器判断，actual 值用于核对真实执行；单次耗时不能直接宣传为稳定性能提升。

#### 12. 为什么数据量较小时，即使存在索引，优化器也可能选择全表扫描？

优化器比较的是预计总成本。表很小或条件命中比例很高时，顺序扫描可能比经过索引再回表更便宜。索引存在不等于必须使用；应在有区分度、接近真实规模的数据上查看计划，并如实记录优化器选择。

### 自测题与参考答案

#### 1. 为什么完整测试开始前必须确认连接的是 `intern_project_test`，而不能只凭环境变量名称判断？

环境变量名只是人为约定，值仍可能被错误配置。必须解析实际 URL，并由数据库执行 `SELECT DATABASE()` 确认当前连接，才能避免清理脚本或测试误操作开发库、生产库或其他数据。

#### 2. 为什么第 6 天要在清理测试数据后连续执行两次 `mvn test`？

第一次通过证明从干净数据库开始时功能、约束和测试初始化可工作；第二次紧接着通过证明测试不会依赖上一次遗留数据，清理和初始化具有可重复性，也能暴露固定用户名、固定主键或顺序依赖等污染问题。

#### 3. 创建资源后停止应用，再启动并按 ID 查询，主要验证了什么？

它验证数据由 MySQL 持久化，不依赖进程内存。只在同一次启动中读取，仍可能是内存对象或缓存返回；进程结束并重启后还能读取，才形成更直接的持久化证据。

#### 4. `schema.sql` 使用 `CREATE TABLE IF NOT EXISTS` 有什么好处？为什么不能长期替代 Flyway？

它便于空库首次初始化，也允许重复执行而不因表已存在立即失败。但它不会记录版本、按顺序升级已有表，也不能可靠处理字段变更、数据迁移和回滚；数据库演进复杂后应使用版本化迁移工具。

#### 5. 为什么文档和工单列表只返回摘要字段，而详情接口仍可返回正文或描述？

列表用于快速浏览，应避免传输和反序列化大文本；详情接口才承担展示完整内容的职责。Mapper 列表 SQL 也只选择摘要列，才能从数据库读取阶段就避免无用的大字段 I/O，而不只是序列化时隐藏字段。

#### 6. 请分别说明 HTTP 400、404、409 在本项目中的典型场景和错误码。

400：例如 `page=0`，返回 `VALIDATION_ERROR`；或非法工单状态查询，返回 `INVALID_REQUEST_PARAMETER`。404：资源 ID 不存在，返回 `RESOURCE_NOT_FOUND`。409：用户名或邮箱违反唯一性，返回 `DUPLICATE_RESOURCE`。

#### 7. 为什么真实数据库凭据应放在环境变量或未纳入 Git 的本地配置中？

凭据属于本机或部署环境秘密，提交 Git 后会进入历史并可能泄漏。仓库只保存无秘密的配置模板和 `${DB_URL}`、`${DB_USERNAME}`、`${DB_PASSWORD}` 等占位符，以及安全的配置说明。

#### 8. 工单状态更新为什么必须把“加锁读取—状态校验—写入”放在同一个事务中？

若三步不在同一事务中，`FOR UPDATE` 的锁可能在校验和更新前失效，两个请求就可能都依据旧状态通过校验。锁在事务提交或回滚时释放；本项目按主键只锁目标工单，减少无关阻塞。

#### 9. `EXPLAIN` 和 `EXPLAIN ANALYZE` 的主要区别是什么？

`EXPLAIN` 只生成估算计划，不真正执行查询；`EXPLAIN ANALYZE` 会执行查询并返回实际统计。至少关注所选索引、估算与实际行数、节点 `loops`、首次产出与完成时间，以及是否出现额外排序、扫描或回表。

#### 10. 请从 HTTP 请求开始，复述一次创建资源写入 MySQL 的主要调用链。

典型链路是：Spring MVC 解析 JSON 并校验 DTO → Controller → Service → Repository 接口 → MyBatis Repository 实现 → Mapper/XML → JDBC → MySQL，结果再反向映射为领域对象和 `ApiResponse`。Repository 接口隔离业务用例和具体持久化技术，使 Service 不依赖 MyBatis，并允许测试替换为轻量实现。
