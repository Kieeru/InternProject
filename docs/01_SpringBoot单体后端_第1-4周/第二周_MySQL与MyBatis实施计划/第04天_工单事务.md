# 第 04 天：工单持久化与事务实施计划

> **供执行者使用：** 实施本计划前必须使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans`，并使用复选框（`- [ ]`）逐项跟踪。

**目标：** 把工单创建、查询和状态更新迁移到 MySQL，并通过事务与行锁保证并发状态流转仍符合领域规则。

**架构：** `TicketService.updateStatus` 作为事务边界，Repository 提供加锁查询；MyBatis 使用 `SELECT ... FOR UPDATE` 获取当前行，Service 基于锁定后的最新状态校验，再由 Mapper 更新。内存实现补齐相同接口以保留快速单元测试。

**技术栈：** Java 21、Spring Boot 4.1.1、MyBatis 4.0.0、MySQL 8.4、Spring `@Transactional`、JUnit 5 并发测试。

**设计规格：** `docs/01_SpringBoot单体后端_第1-4周/2026-10-06_MySQL与MyBatis持久化设计.md`

## 全局约束

- 状态顺序仍为 `PENDING → PROCESSING → RESOLVED → CLOSED`，跳级、回退、重复和关闭后更新都拒绝。
- 工单状态列使用 `VARCHAR(32)` 与数据库 CHECK，不改用 MySQL ENUM。
- Service 承担事务和业务校验；Mapper 不判断合法状态，不抛用户业务异常。
- `SELECT ... FOR UPDATE` 必须在有效事务内使用；事务中不调用外部服务或执行无关耗时操作。
- 并发结论必须来自真实 MySQL，不用 Mock 或内存 Repository 代替。

## 审查重点

- 两个相同并发更新是否错误地都返回成功。
- 加锁查询是否遗漏 `deleted = 0`。
- `@Transactional` 是否因自调用或非 Spring Bean 而失效。
- 更新影响行数不是 1 时是否被忽略。
- 行锁是否保持到状态校验和更新完成之后再释放。
