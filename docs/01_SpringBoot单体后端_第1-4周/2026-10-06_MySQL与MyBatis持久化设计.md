# 第二周 MySQL 与 MyBatis 持久化设计规格

## 1. 文档状态

- 设计日期：2026-10-06
- 所属阶段：Spring Boot 单体后端，第 2 周——MySQL 与 MyBatis
- 设计状态：书面规格已批准，实施计划待审阅
- 实施约束：实施计划获批且用户选择执行方式前不修改生产代码；实施时遵循测试先行，并保持现有 HTTP 行为兼容

## 2. 背景与目标

第一周已经完成用户、知识文档和工单三个纵向业务切片。当前 Controller 只依赖 Service，Service 只依赖 Repository 接口，Repository 的实现使用 `ConcurrentHashMap` 和 `AtomicLong`。现有分层已经为替换存储实现提供了边界。

第二周的目标不是扩展认证、对象存储或微服务，而是完成以下最小、可验证的持久化增量：

1. 使用 MySQL 持久化用户、文档和工单，应用重启后数据不丢失。
2. 完成用户、角色、权限及其关联表，为后续 RBAC 提供数据结构，但本周不实现登录和鉴权。
3. 使用原生 MyBatis 编写可见、可解释的 SQL。
4. 为文档和工单增加分页及条件查询。
5. 使用事务和行锁保证工单状态流转在并发请求下仍满足业务规则。
6. 使用真实 MySQL 执行集成测试及 `EXPLAIN ANALYZE`，形成可复现证据。

本次迁移必须保留现有创建、按 ID 查询和工单状态更新接口的路径、HTTP 状态、响应结构、中文消息和错误码。

## 3. 技术选择

### 3.1 MyBatis

本周采用原生 MyBatis，不采用 MyBatis-Plus，也不混用两套 Starter。

选择原因：

- 第二周需要直接学习 SQL 映射、动态查询、分页、事务、锁和执行计划。
- 显式 SQL 更容易把 Java 请求链路与数据库行为对应起来。
- 当前只有三个业务模块，手写 SQL 的维护成本可控。
- 官方 MyBatis Spring Boot Starter 4.x 与当前 Spring Boot 4.1.1 和 Java 21 匹配。

Mapper 接口只描述数据库操作；动态条件查询、分页查询和加锁查询使用 XML 编写。Repository 实现负责把 Mapper 隔离在现有 Repository 接口之后，Service 不直接依赖 Mapper。

### 3.2 MySQL

数据库使用本机已经安装并运行的 MySQL 8.4 LTS。Docker 守护进程当前没有运行，因此 Docker Compose 不作为本周实施前置条件，也不启用 Spring Docker Compose 集成。

生产开发库和测试库必须分开：

- 开发库：`intern_project`
- 测试库：`intern_project_test`

数据库地址、用户名和密码通过环境变量或未纳入 Git 的 `application-local.properties` 提供。仓库中不保存真实密码。

### 3.3 暂不引入的组件

- 不引入 JPA 或 Hibernate。
- 不引入 Flyway；本周使用显式初始化脚本学习 DDL，后续出现多版本迁移需求时再评估。
- 不使用 H2 代替 MySQL，因为 DDL、索引、锁和 SQL 方言存在差异。
- 不提前引入 Redis、Spring Cloud、MinIO、Kafka、认证或 Testcontainers。

## 4. 分层与组件边界

持久化后的调用链如下：

```text
HTTP 请求
    ↓
Controller：参数校验、HTTP 状态、响应封装
    ↓
Service：业务规则、事务边界、异常语义
    ↓
Repository 接口：领域需要的持久化契约
    ↓
MyBatis Repository 实现：领域对象与 Mapper 结果之间的适配
    ↓
Mapper 接口 + XML：SQL 与结果映射
    ↓
MySQL
```

约束：

- Controller 不访问 Repository 或 Mapper。
- Service 不依赖具体 MyBatis 类型。
- Mapper 不判断工单能否流转，不抛面向用户的业务异常。
- `InMemory*Repository` 不再作为运行时默认 Bean，但保留为 Service 单元测试的轻量测试替身。
- 数据库审计字段不直接加入现有创建和详情接口的 JSON，避免无意改变公开响应；列表接口使用专门的摘要响应 DTO。

建议新增的持久化结构位于现有 `repository/` 边界内：

```text
repository/
├── UserRepository.java
├── DocumentRepository.java
├── TicketRepository.java
├── InMemory*Repository.java
└── mybatis/
    ├── MyBatisUserRepository.java
    ├── MyBatisDocumentRepository.java
    ├── MyBatisTicketRepository.java
    └── mapper/
        ├── UserMapper.java
        ├── DocumentMapper.java
        └── TicketMapper.java

resources/
├── mapper/
│   ├── UserMapper.xml
│   ├── DocumentMapper.xml
│   └── TicketMapper.xml
└── db/
    └── schema.sql
```

角色和权限本周只需要 DDL 与必要的数据库验证；在出现 RBAC 用例前，不创建空洞的 Controller、Service 或 Repository。

## 5. 数据模型

### 5.1 通用约定

主业务表统一使用：

- `id BIGINT AUTO_INCREMENT` 主键。
- `created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)`。
- `updated_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6)`。
- `deleted TINYINT(1) NOT NULL DEFAULT 0`，其中 `0` 表示有效、`1` 表示已逻辑删除。
- InnoDB 存储引擎和 `utf8mb4` 字符集。

所有正常查询显式包含 `deleted = 0`。用户名和邮箱在逻辑删除后仍不允许重新注册，以保持身份标识和未来审计语义稳定。

### 5.2 `users`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | `BIGINT` | 主键、自增 |
| `username` | `VARCHAR(64)` | 非空、唯一 |
| `email` | `VARCHAR(254)` | 非空、唯一 |
| `created_at` | `DATETIME(6)` | 非空 |
| `updated_at` | `DATETIME(6)` | 非空 |
| `deleted` | `TINYINT(1)` | 非空、默认 0 |

本周不增加密码字段。密码哈希、登录和 Token 属于第六周认证范围。

### 5.3 `roles`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | `BIGINT` | 主键、自增 |
| `code` | `VARCHAR(64)` | 非空、唯一，机器可读标识 |
| `name` | `VARCHAR(64)` | 非空，中文显示名称 |
| `description` | `VARCHAR(255)` | 可空 |
| 通用字段 |  | `created_at`、`updated_at`、`deleted` |

本周不预置角色数据，避免在鉴权规则未设计前固化含义。

### 5.4 `permissions`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | `BIGINT` | 主键、自增 |
| `code` | `VARCHAR(100)` | 非空、唯一，机器可读标识 |
| `name` | `VARCHAR(64)` | 非空，中文显示名称 |
| `description` | `VARCHAR(255)` | 可空 |
| 通用字段 |  | `created_at`、`updated_at`、`deleted` |

本周不定义接口级权限清单，权限编码在第六周根据实际用例增加。

### 5.5 `user_roles`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `user_id` | `BIGINT` | 外键引用 `users.id` |
| `role_id` | `BIGINT` | 外键引用 `roles.id` |
| `created_at` | `DATETIME(6)` | 非空 |

`(user_id, role_id)` 为联合主键，防止重复授权。外键使用 `ON DELETE RESTRICT`；正常业务只做逻辑删除。

### 5.6 `role_permissions`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `role_id` | `BIGINT` | 外键引用 `roles.id` |
| `permission_id` | `BIGINT` | 外键引用 `permissions.id` |
| `created_at` | `DATETIME(6)` | 非空 |

`(role_id, permission_id)` 为联合主键，防止重复授权。该联合主键也能覆盖“按角色查询权限 ID”的查询。

### 5.7 `documents`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | `BIGINT` | 主键、自增 |
| `title` | `VARCHAR(200)` | 非空 |
| `content` | `LONGTEXT` | 非空 |
| 通用字段 |  | `created_at`、`updated_at`、`deleted` |

本周继续存储现有纯文本正文。对象存储地址、文件类型、版本和访问权限在第七周 MinIO 与文档业务扩展时设计。

### 5.8 `tickets`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | `BIGINT` | 主键、自增 |
| `title` | `VARCHAR(200)` | 非空 |
| `description` | `TEXT` | 非空 |
| `status` | `VARCHAR(32)` | 非空、默认 `PENDING`、带状态 CHECK 约束 |
| 通用字段 |  | `created_at`、`updated_at`、`deleted` |

状态使用 `VARCHAR + CHECK`，不使用 MySQL `ENUM`，以便后续加入“重新打开”等状态时通过普通脚本演进。当前允许值为 `PENDING`、`PROCESSING`、`RESOLVED`、`CLOSED`。

本周不增加创建人、处理人、优先级或操作历史，因为当前 API 没有认证用户上下文，这些字段无法被可靠赋值。

## 6. Repository 与查询契约

### 6.1 已有契约

创建和按 ID 查询的外部行为保持不变。数据库负责生成主键，Repository 在插入后返回带 ID 的领域对象。

逻辑删除记录在 `findById` 中视为不存在，Service 继续映射为 `RESOURCE_NOT_FOUND`。

### 6.2 列表查询

本周新增两个列表接口：

- `GET /tickets?status=&keyword=&page=1&size=20`
- `GET /documents?titlePrefix=&page=1&size=20`

统一规则：

- 页码从 1 开始。
- 默认每页 20 条，最大 100 条。
- 页码小于 1、条数小于 1 或大于 100 时返回 HTTP 400 和稳定的中文校验消息。
- 排序固定为 `created_at DESC, id DESC`，相同时间下仍保持稳定顺序。
- 工单 `keyword` 匹配标题；文档 `titlePrefix` 只做前缀匹配，以便观察 B+Tree 索引行为。
- 列表响应使用 `ApiResponse<PageResponse<SummaryDto>>`。
- 工单摘要包含 `id`、`title`、`status`、`createdAt`；文档摘要包含 `id`、`title`、`createdAt`，不返回大文本正文。

Repository 的分页输入使用查询对象封装条件、偏移量和条数，不把 HTTP 参数类型传入 Repository。分页输出同时包含当前页数据和总记录数。

## 7. 索引设计

除主键和唯一约束产生的索引外，增加：

1. `tickets(status, deleted, created_at DESC, id DESC)`：服务于指定状态的稳定分页。
2. `tickets(deleted, created_at DESC, id DESC)`：服务于不指定状态的稳定分页。
3. `documents(deleted, title, id)`：服务于未删除文档的标题前缀查询。

不为 `LIKE '%关键字%'` 建立普通 B+Tree 索引并声称可以优化，因为前导通配符无法有效使用普通索引。工单标题模糊匹配保留为小数据量功能，执行计划中应如实说明它仍可能需要扫描候选记录。

本周使用 `EXPLAIN ANALYZE` 验证：

1. 指定状态的工单分页查询是否使用联合索引，并观察估算行数与实际行数。
2. 文档标题 `LIKE 'Spring%'` 是否使用标题联合索引。
3. 额外比较 `LIKE '%Spring%'`，解释前导通配符对索引使用的影响。
4. 验证 `role_permissions` 联合主键对“按角色查询权限 ID”形成覆盖索引。

执行计划和结论记录到当天 handoff；只记录真实执行结果，不预填性能收益。

## 8. 工单事务与并发

### 8.1 风险

当前状态更新流程是“读取当前状态—校验—写入目标状态”。如果数据库实现仍把三步放在互不关联的语句中，两个并发请求可能同时读到 `PENDING`，都通过校验，并都返回更新成功，违反重复状态变更应被拒绝的规则。

### 8.2 事务边界

`TicketService.updateStatus` 是事务边界。一次状态变更必须在同一事务中完成：

1. 通过 `SELECT ... FOR UPDATE` 查询未删除工单并锁定目标行。
2. 工单不存在时抛出原有资源不存在异常。
3. 使用领域枚举校验当前状态是否能流转到目标状态。
4. 执行状态更新并检查受影响行数必须为 1。
5. 返回更新后的工单；提交事务后释放行锁。

事务内不得调用外部服务或执行耗时操作。该方案选择悲观行锁，是因为状态流转冲突需要立即基于最新状态给出确定结果，而且当前每次只锁定一个工单，死锁风险较低。

### 8.3 验证行为

并发测试同时提交两个 `PENDING → PROCESSING` 请求，期望一个成功，另一个在获取锁后看到最新状态并返回 `INVALID_STATUS_TRANSITION`。最终数据库状态必须为 `PROCESSING`。

## 9. 配置与初始化

配置分为：

- 公共配置：应用名、MyBatis Mapper XML 路径、下划线转驼峰策略。
- 本地 MySQL 配置：从环境变量读取开发库连接信息。
- MySQL 测试配置：从环境变量读取独立测试库连接信息。
- 内存测试配置：只为不需要 Spring 数据库上下文的快速 Service 测试保留。

`schema.sql` 必须可在空数据库上重复执行；使用 `CREATE TABLE IF NOT EXISTS`，按被引用表先于关联表的顺序创建。应用启动不自动删除或重建表。

DDL 账户与应用运行账户概念上分离：初始化脚本可以使用有建表权限的本地管理账户，应用账户只需要业务表的查询和写入权限。第二周本地练习可以先使用现有 MySQL 账户，但 README 必须明确最小权限方向。

## 10. 测试策略

### 10.1 快速单元测试

- 现有 Service 测试继续直接构造 `InMemory*Repository`。
- 验证业务状态机、资源不存在和对象创建等领域行为。
- 这些测试不启动 Spring，也不连接数据库。

### 10.2 MyBatis Repository 集成测试

- 使用真实 `intern_project_test` MySQL 数据库。
- 覆盖插入后主键回填、按 ID 查询、逻辑删除过滤、状态更新、分页条件和结果映射。
- 每个测试通过事务回滚或显式清理保证隔离。
- 不使用 Mock Mapper 验证数据库 SQL。

### 10.3 HTTP 集成测试

- 保留现有创建、查询、参数校验、404 和状态流转测试。
- 增加应用重启后可查询的手工验证流程。
- 增加两个列表接口的空结果、默认分页、条件查询、非法分页参数测试。
- 选择至少一组 HTTP 测试连接真实 MySQL，证明 Controller 到数据库的完整链路。

### 10.4 并发回归测试

- 使用两个独立事务并发更新同一工单。
- 验证只有一次状态变更成功。
- 验证最终数据库状态以及失败响应错误码。

完整验收仍以 `mvn test` 为标准。在持久化测试加入后，执行前必须保证测试库可连接并已初始化。最终报告测试总数、失败数、错误数和警告，不沿用历史数字。

## 11. 实施顺序与 TDD 检查点

### 阶段 A：数据库基础

1. 先编写数据库结构验证或 Repository 失败测试。
2. 创建 `schema.sql`。
3. 建立开发库和测试库配置。
4. 验证空数据库能通过脚本完整初始化。

### 阶段 B：用户纵向切片，由用户主导

1. 定义用户 Repository 数据库测试。
2. 确认测试因数据库实现缺失而失败。
3. 编写 User Mapper SQL 和 Repository 适配器。
4. 验证创建、主键回填、查询、唯一约束和 404 行为。
5. 复述一次 Controller 到 MySQL 的完整链路并接受代码审查。

### 阶段 C：文档和工单基础迁移

按照已经验证的用户模式迁移文档和工单创建、按 ID 查询，不同时引入分页或事务复杂度。每个模块单独完成红—绿—重构循环。

### 阶段 D：工单事务

1. 先增加并发回归测试。
2. 确认无锁实现出现不符合预期的结果。
3. 加入 Service 事务边界和加锁查询。
4. 再次验证串行状态流转、非法流转和并发流转。

### 阶段 E：分页与索引

1. 先定义列表接口行为和失败测试。
2. 实现查询对象、摘要 DTO、分页结果和 Mapper 动态 SQL。
3. 准备有区分度的测试数据。
4. 执行 `EXPLAIN ANALYZE`，根据真实计划确认或调整索引。

### 阶段 F：完整验收

1. 运行完整 `mvn test`。
2. 启动应用并实际验证创建、重启、查询、分页和状态更新。
3. 检查 Git 状态，确认没有密码、日志、数据库文件或构建产物进入版本控制。
4. 更新 README 和当天 handoff，记录真实测试与执行计划证据。

## 12. 本阶段必学基础知识与基础练习

### 12.1 学习目标

本阶段的学习目标不是记住所有 MySQL 配置或 MyBatis API，而是能够独立回答以下问题：

1. 一张表为什么需要这些字段、约束和索引？
2. 一条 Java 方法最终执行了什么 SQL，参数和结果是怎样映射的？
3. 为什么某条查询使用或没有使用索引？
4. 为什么工单状态更新必须放在事务中，并对目标记录加锁？
5. 如何用自动化测试、两会话实验和执行计划证明结论？

学习采用“小循环”方式：学习一个知识点 30～60 分钟，完成最小练习，再立即应用到项目。不要先连续学习数天理论后才开始数据库设计。

### 12.3 基础练习一：表、约束与关联

在独立的练习库中建立最小的 `practice_users`、`practice_roles` 和 `practice_user_roles` 三张表，不直接修改项目正式表。

练习步骤：

1. 为用户表设置自增主键、用户名唯一约束、邮箱唯一约束和创建时间。
2. 为关联表设置联合主键和两个外键。
3. 插入 3 个用户和 2 个角色，并建立用户与角色的多对多关系。
4. 故意插入重复邮箱，观察唯一约束错误。
5. 故意插入不存在的用户 ID，观察外键约束错误。
6. 使用连接查询返回“用户名—角色编码”。

验收方式：用户能够说明为什么关联表不能只使用一个普通自增 ID，以及数据库约束与 Java 参数校验分别解决什么问题。

### 12.4 基础练习二：事务与回滚

在 MySQL 客户端中手动执行一次事务：

1. 关闭当前操作的自动提交或显式执行 `START TRANSACTION`。
2. 插入一条练习用户，再在同一事务中查询到它。
3. 执行 `ROLLBACK`。
4. 在事务外确认该记录不存在。
5. 再执行一次插入并 `COMMIT`，确认记录持久存在。

验收方式：用户能够说明“事务中的可见”和“提交后的持久化”不是同一概念，并能说出异常导致回滚时哪些 SQL 必须属于同一事务。

### 12.5 基础练习三：两个会话观察行锁

同时打开 MySQL 会话 A 和会话 B，对同一条练习工单操作：

1. 会话 A 开启事务并执行 `SELECT ... FOR UPDATE`，暂不提交。
2. 会话 B 尝试更新同一行，观察其等待状态。
3. 会话 A 更新状态并提交。
4. 会话 B 继续执行后，重新读取最新状态。
5. 重复一次，但会话 A 只做普通 `SELECT`，比较两次行为。

验收方式：用户能够解释为什么 `FOR UPDATE` 必须位于事务中、锁何时释放，以及锁定单行与锁定大量记录对并发的影响。

### 12.6 基础练习四：联合索引与执行计划

为练习工单准备至少 1,000 条具有不同状态和创建时间的数据，用同一条“按状态、按创建时间倒序分页”的查询完成对比：

1. 没有业务联合索引时执行 `EXPLAIN ANALYZE`。
2. 建立 `(status, deleted, created_at DESC, id DESC)` 后再次执行。
3. 去掉查询中的 `status` 条件，观察为什么需要另一条以 `deleted` 开头的分页索引。
4. 比较文档标题 `LIKE 'Spring%'` 与 `LIKE '%Spring%'` 的执行计划。

需要记录使用的索引、扫描行数、估算行数、实际行数和实际耗时。单次耗时只用于观察，不据此宣称稳定的性能提升。

验收方式：用户能够根据查询条件、排序和返回列说明最左前缀、范围条件、回表和覆盖索引，而不是背诵“加索引会变快”。

### 12.7 基础练习五：最小 MyBatis 映射

MyBatis 不另外创建玩具项目，直接把用户持久化切片作为最小练习，并由用户主导：

1. 先写 `UserRepository` 数据库测试，覆盖保存、主键回填和按 ID 查询。
2. 定义只包含插入和按 ID 查询的 `UserMapper`。
3. 在 XML 中使用 `#{}` 绑定参数，不使用 `${}` 拼接用户输入。
4. 配置插入后的自增主键回填。
5. 使用明确的结果映射把下划线字段转换为 Java 属性。
6. 通过 Repository 适配器返回领域对象，Service 不接触 Mapper。

验收方式：用户能够从 `POST /users` 开始，依次指出 Controller、Service、Repository、Mapper、SQL 和 MySQL 的职责，并解释 `#{}` 为什么比直接字符串替换安全。

### 12.8 基础练习输出与检查点

完成练习后，应保留下列可复查证据：

- 三张练习表及约束的 SQL，保存位置在实施计划中确定，不能包含密码。
- 一份两会话行锁实验记录，包括执行顺序和观察到的等待行为。
- 至少两条真实 `EXPLAIN ANALYZE` 结果及用户自己的结论。
- 用户模块的失败测试、最小 MyBatis 实现和通过结果。
- 一段用自己的语言写出的完整请求链路说明。

进入项目各步骤前设置三个学习检查点：

1. 开始正式 DDL 前，先通过表与约束练习。
2. 开始工单事务实现前，先通过两会话行锁练习。
3. 确定最终索引前，先完成执行计划对比；索引设计允许根据实测调整。

## 14. 验收标准

设计实施完成必须同时满足：

- 现有七个接口的成功和失败行为没有回退。
