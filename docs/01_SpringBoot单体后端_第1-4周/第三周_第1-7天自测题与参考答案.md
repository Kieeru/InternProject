### 自测题与参考答案

#### 1. `已完成问答` String、Hash、Set、ZSet 各适合什么业务？为什么本计划的文档值选 String JSON？

String 适合保存一个整体标量、文本、计数或序列化后的 JSON；Hash 适合按字段读取和修改对象；Set 适合无序去重集合；ZSet 为成员附加分数，适合排行榜、优先级和按时间排序。List 是按插入顺序排列的字符串序列，可用于简单队列或时间线，但不能直接替代具有可靠投递要求的消息系统。

本项目按 ID 读取时需要把一篇文档作为一个完整快照返回，并统一设置版本、类型标记和 TTL，因此选择 String JSON 更直接。String 能保存较大的值不代表适合无限大的值；本计划超过 512 KiB 就绕过缓存，防止大 Key 增加网络、内存和事件循环压力。

#### 2. `已完成问答` Redis Key 到期后一定会在到期瞬间物理删除吗？

不一定。Redis 会在访问 Key 时检查 TTL，发现过期后执行惰性删除；后台还会定期抽样检查带过期时间的 Key，并根据过期比例继续清理。过期 Key 可能短暂占用内存，但读取时不会再作为有效值返回。TTL 解决逻辑有效期，不能用来承诺某个任务会在某一毫秒准时执行。

#### 3. `已完成问答` RDB 和 AOF 的主要差别是什么？为什么本项目不能靠它们保证业务事实？

RDB 保存某个时间点的数据快照，可以由保存规则、`BGSAVE` 等机制触发，文件紧凑且恢复通常较快，但两次快照之间的数据可能丢失。AOF 追加记录写命令，不记录 GET 等只读命令；它通常能缩小数据丢失窗口，但文件更大，需要重写和命令重放，具体可靠性还取决于刷盘策略。

两者都只是 Redis 自身的恢复手段，不会把缓存变成事实数据源。缓存可能过期、被淘汰、被清空或因故障丢失；本项目必须能从 MySQL 重建文档和权限缓存，工单最终也必须写入 MySQL。

#### 4. `已完成问答` `allkeys-lfu` 与 `volatile-ttl` 的选择依据是什么？

`allkeys-lfu` 可以从所有 Key 中近似淘汰访问频率最低的 Key，适合整个实例都是可重建缓存、所有 Key 都允许丢失的场景。`volatile-ttl` 只从设置了 TTL 的 Key 中选择，并倾向淘汰剩余 TTL 更短的 Key；没有 TTL 的 Key 不会成为候选。

选择依据是实例用途、哪些数据允许丢失、是否能保证缓存 Key 都有 TTL，以及希望按热度还是按剩余生命周期回收。若一个实例混有无 TTL 数据，`volatile-ttl` 可能因可淘汰候选不足而无法释放足够内存。本项目当前开发实例实测为 `noeviction`，不会在第一天擅自修改全局策略；若以后使用纯缓存实例，再评估 `allkeys-lfu`。

#### 5. `已完成问答` 为什么不能把“Docker CLI 已安装”等同于“Redis 可运行”？

Docker CLI 只是向 Docker Engine 发送请求的客户端。完整验证还要确认 Docker Engine 正在运行、Redis 容器已创建并处于 `healthy`、端口按预期绑定，以及容器内 Redis 真能处理命令。本项目的证据链是：Docker/Compose 版本可读、`docker compose ps` 显示 healthy、端口只绑定 `127.0.0.1:6379`，最后 `redis-cli PING` 返回 `PONG`。

## 第 2 天：热门知识文档缓存旁路与 TTL 抖动

- String JSON 序列化、Key 版本与缓存对象大小控制。
- TTL 随机抖动如何降低同批 Key 集中过期风险。
- 为什么详情缓存与分页缓存具有不同的失效复杂度。

### 自测题与参考答案

#### 1. `已完成问答` cache-aside 与 read-through 有什么区别？当前方案属于哪一种？

cache-aside 由应用显式编排：先查缓存，未命中再查 MySQL，最后尝试回填缓存；更新时也由应用决定何时失效。read-through 则由缓存组件把“未命中时加载数据”的能力封装起来，调用方只面向缓存读取。

本项目采用 cache-aside。`DocumentService` 仍负责用例编排，并分别依赖文档 Repository 和文档缓存端口；Redis 不隐藏 MySQL，也不成为 Repository 的事实实现。

#### 2. `已完成问答` 为什么分页查询暂不缓存？

分页 Key 会组合标题前缀、页码、页大小和排序条件，容易产生大量低复用 Key。新增、更新或删除一篇文档后，可能影响许多页及总数，失效范围难以精确控制。本周先缓存收益明确、Key 稳定的按 ID 详情，不为低收益场景增加复杂失效逻辑。

#### 3. `已完成问答` TTL 为什么要有随机抖动，为什么不能给所有文档同一个精确过期时间？

如果一批 Key 在同一时间写入并使用完全相同的 TTL，它们可能集中失效，使大量请求同时回源 MySQL，形成缓存雪崩。把 TTL 设为“基础值 + 有界随机抖动”可以分散过期时间。本项目文档正值计划使用 10 分钟加 0～120 秒，测试必须通过可控随机源验证上下界，而不能依赖随机碰巧取值。

#### 4. `已完成问答` 为什么 Key 要包含 `v1`？

Key 中的版本表示缓存值结构和语义版本。JSON 字段、类型标记或序列化规则发生不兼容变化时，可以改为 `v2`，让新旧数据自然隔离并等待旧 Key 过期，而不需要在启动时执行危险的全库清理。

#### 5. `已完成问答` 512 KiB 限制解决什么风险，超过限制后的正确行为是什么？

它限制单个文档缓存值的内存、网络传输、序列化和 Redis 事件循环成本，避免形成大 Key。超过限制时仍应把 MySQL 查询结果正常返回给调用方，只跳过缓存写入；不能因为缓存优化失败而把成功的核心查询变成 HTTP 500，也不能截断正文后缓存错误数据。第 2 天实现以 `put=false` 表达跳过，第 3 天再把该行为记录为 `bypass` 指标。

能够画出“缓存读取 → 未命中 → MySQL → 尝试回填”的链路，说明 Key 版本、TTL 抖动和大值绕过分别控制什么风险，并解释为什么文档列表仍直接查询 MySQL。

## 第 3 天：空值缓存、故障降级与命中率

> 状态：`已完成问答`。2026-10-18 已完成空值条目、Redis 故障和损坏值回退、统计器、统计接口及真实停启 Redis 验收；用户已不看参考答案完成五道检查题，并完成关键概念纠正与复盘。

### 应掌握的内容

- 缓存穿透、击穿和雪崩的区别。
- 空值缓存与布隆过滤器的适用边界。
- Redis 超时、连接失败和损坏缓存值的降级策略。
- 命中率分母、错误计数和绕过计数的含义。

### 自测题与参考答案

#### 1. `已完成问答` 缓存穿透、击穿、雪崩分别指什么？

穿透是大量请求查询根本不存在的数据，缓存和数据库都无法命中，导致请求持续到达数据库。击穿是某个热点 Key 失效时，大量并发请求同时回源重建。雪崩是大量 Key 集中过期或整个 Redis 不可用，使广泛请求在短时间内同时压向数据库。三者影响范围和治理手段不同，不能混为同一个问题。

#### 2. `已完成问答` 空值缓存相比布隆过滤器有什么优缺点？

空值缓存实现简单，可以精确表达某个 ID 暂时不存在，并通过短 TTL 自动收敛；缺点是恶意请求大量随机 ID 时仍会产生很多空值 Key，而且新建资源后必须及时失效对应空值。布隆过滤器空间效率高，能在访问 Redis 正文缓存或数据库前快速排除大量必不存在值，但存在误判、重建和删除困难，也增加数据同步成本。本项目规模较小，先采用短 TTL 空值缓存。

#### 3. `已完成问答` 为什么 `error` 不直接计入命中率分母？

命中率衡量“缓存正常参与查询时，有多少查找由缓存回答”，因此分母使用 `hit + negativeHit + miss`。Redis 连接错误、超时或损坏数据属于可用性问题；把它们混入分母会把缓存效果和缓存故障混成一个指标。`error` 与功能关闭或大值导致的 `bypass` 应单独展示。

#### 4. `已完成问答` 哪些异常可以降级，为什么不能 `catch (RuntimeException)` 后全部忽略？

可以降级的是预期的缓存依赖失败，例如 Redis 连接异常、命令超时和明确的缓存序列化/反序列化失败。应用应记录错误并回源 MySQL。不能吞掉所有 `RuntimeException`，因为空指针、参数错误、状态机缺陷等编程错误也会被掩盖，系统可能返回看似成功但实际错误的数据，使缺陷无法被测试和监控发现。

#### 5. `已完成问答` 空值 TTL 为什么应明显短于正值 TTL？

“不存在”比已有文档更容易因新建数据而快速变化。如果空值缓存过久，即使 MySQL 中已经创建对应资源，旧的 `MISSING` 仍可能继续返回 404。短 TTL 可以降低这个陈旧窗口；同时创建或更新提交后仍应主动删除对应 Key，而不能只依赖过期。

## 第 4 天：热点 Key 重建与数据库提交后失效

> 状态：`已完成问答`。2026-10-18 已完成文档更新 API、事务提交后失效、3 秒 Redis 重建锁、token + Lua 安全释放、有限等待、真实 Redis 并发测试和故障降级验收；用户已不看参考答案完成五道检查题，并完成一致性与降级边界的纠正和复盘。

### 应掌握的内容

- `SET key token NX PX` 的互斥语义和锁过期时间。
- token 与 Lua 比较删除如何避免误删他人锁。
- 热点 Key 重建等待上限和数据库降级。
- 更新数据库、事务提交和删除缓存的顺序。
- 缓存旁路的一致性边界。

### 自测题与参考答案

#### 1. `已完成问答` `SETNX` 后为什么必须有过期时间？

持锁进程可能崩溃、网络中断或执行超时。如果锁没有 TTL，它可能永久存在，后续请求永远无法成为重建者。获取锁时应原子地同时设置 NX 与过期时间，不能先 `SETNX` 再单独 `EXPIRE`，否则两条命令之间崩溃仍会留下无期限锁。

#### 2. `已完成问答` 为什么释放锁前要比较 token？直接 `DEL` 有什么竞态？

持有者执行时间可能超过锁 TTL：旧锁已过期，新请求已经取得同名新锁。旧持有者此时直接 `DEL` 会删除新请求的锁。每次获取时生成唯一 token，释放时用 Lua 在 Redis 内原子执行“值等于自己的 token 才删除”，才能避免检查和值删除之间被其他命令插入，也避免误删他人锁。

#### 3. `已完成问答` 为什么采用“更新数据库，提交后删除缓存”？

MySQL 是事实来源，必须先让数据库事务成功。若先删缓存再更新数据库，并发读可能在数据库提交前读到旧值并重新写入缓存；若事务提交前删除而数据库最终回滚，也会产生无意义失效。提交后删除让下一次读取从已提交的新值重建缓存。

#### 4. `已完成问答` 该方案为什么仍不是强一致？最坏陈旧时间由什么决定？

数据库提交到缓存删除之间仍有一个很短窗口，并发请求可能读到旧缓存；删除命令本身也可能因 Redis 故障失败。即使删除成功，更早开始的查询也可能先读到旧 MySQL 值，再在删除后把它回填缓存。旧值最终要等 TTL 到期才自然消失，因此最坏陈旧时间主要受旧缓存剩余 TTL 影响。本周接受最终一致性，不提前引入消息队列、分布式事务或延迟双删。

#### 5. `已完成问答` 锁等待者为什么必须有超时和数据库降级路径？

重建者可能变慢、崩溃或无法回填。等待者若无限阻塞，会耗尽请求线程并放大故障。它们只能短暂重试缓存；达到最大等待时间后直接查询 MySQL，保证核心读取可用。短锁用于减少并发回源，不应成为新的单点故障。

### 掌握标准

能够说明原子加锁、安全释放、有限等待和回源之间的关系，并画出“数据库事务提交 → AFTER_COMMIT 删除缓存 → 下次查询重建”的更新链路及其最终一致性限制。

## 第 5 天：用户权限读取与缓存

> 状态：`已完成问答`。2026-10-19 已完成第 5 天 TDD 增量、真实 Redis 与故障降级验收，并完成五道学习检查；本周只构建权限读取和缓存能力，未提前实现登录、鉴权或角色管理 API。

- RBAC 中用户、角色、权限及关联表的关系。
- 多角色权限去重、稳定排序和空集合缓存。
- 用户不存在与存在但没有权限的语义区别。
- 权限变更后的事务提交后失效。
- 权限数据的敏感边界。

### 自测题与参考答案

#### 1. `已完成问答` 为什么权限码天然需要去重和稳定排序？

一个用户可能通过多个角色获得同一个权限，JOIN 会产生重复行，因此 Repository 查询或 Service 结果必须去重。稳定排序使同一权限集合产生确定的 JSON，方便测试、比较和排查，也避免数据库返回顺序变化造成无意义的缓存值变化。

#### 2. `已完成问答` “用户不存在”和“用户存在但权限为空”为什么不能混为一谈？

用户不存在通常应沿用资源不存在语义；用户存在但没有角色或权限则是合法的空集合。如果都用空值表示，调用方无法判断是无权限还是无用户，也可能让已经删除或错误的用户被当作正常用户处理。缓存值也必须区分 MISS、空权限集合命中和用户不存在。

#### 3. `已完成问答` 权限缓存 TTL 为什么比普通静态文档短？

权限变化会影响用户可以执行的操作，陈旧权限可能造成安全或可用性问题；文档内容通常可以容忍更长的短暂陈旧。因此权限缓存计划使用 5～6 分钟，而文档使用 10～12 分钟。TTL 只是兜底，发生角色关系变更后仍需主动失效。

#### 4. `已完成问答` 第 6 周修改用户角色关系后，应在事务的哪个阶段清理权限缓存？

应在数据库事务成功提交后清理。提交前清理但事务最终回滚，会造成不必要的缓存未命中；更危险的是在数据库新关系尚未可见时让并发读取重建旧权限。提交后失效保证下一次回源读取的是已提交关系。

#### 5. `已完成问答` 为什么本周不开放“查询任意用户权限”的公开接口？

本周尚未实现认证和授权，公开接口会允许未验证调用者枚举他人的权限信息，扩大数据暴露面。当前目标是练习 Repository、Service 和缓存边界，为第 6 周 RBAC 提供内部能力，而不是提前提供缺乏安全保护的 API。

## 第 6 天：工单短窗口重复提交保护

> 状态：`已完成问答`。2026-10-19 已完成第 6 天 TDD 增量与真实 Redis 正常/停机/恢复验收；2026-10-20 用户不看参考答案完成五道学习检查并完成纠正复盘。10 秒内容指纹只是教学版短窗口防重，不得宣传为完整幂等方案。

### 应掌握的内容

- 分布式互斥、短窗口防重和完整幂等的区别。
- 请求指纹和 Key 隐私。
- fail-open 与 fail-closed 的可用性取舍。
- 保存失败时的 token 安全释放。
- 客户端幂等键和持久化结果重放的价值。

### 自测题与参考答案

#### 1. `已完成问答` 分布式锁为什么不等于完整幂等？

锁只在持有期间限制并发进入；锁过期后相同请求仍可再次执行，也不会保存首次业务结果供重试复用。进程崩溃、客户端超时、长时间重试和跨窗口重复都可能绕过短锁。完整幂等通常需要稳定的客户端幂等键、持久化处理状态和结果，并能对同一键重放相同响应。

#### 2. `已完成问答` 为什么 Key 中存 SHA-256 而不是标题和描述原文？

摘要可以让 Key 长度固定，避免工单正文直接出现在 Redis Key、日志和运维工具中，也减少长 Key 的内存和传输成本。SHA-256 的碰撞概率对本练习足够低，但摘要不是加密授权机制；能看到原始内容的人仍可计算相同指纹。

#### 3. `已完成问答` fail-open 与 fail-closed 各自保护什么，本项目为什么选前者？

fail-open 在 Redis 不可用时继续写 MySQL，优先保证核心工单创建可用，代价是故障期间可能出现重复工单。fail-closed 会拒绝或阻塞创建，能更严格保护防重规则，但把 Redis 故障扩大为核心功能不可用。本项目的短窗口防重只是辅助能力，因此选择 fail-open，并单独记录降级。

#### 4. `已完成问答` 保存成功后为什么不立即删除防重 Key？

防重 Key 代表整个 10 秒业务窗口，而不只是数据库写入期间的互斥。保存后立即删除会让紧接着到来的相同重试再次创建工单。成功后应让 Key 保留到 TTL 自然到期；只有 MySQL 保存失败时，才安全释放自己持有的 token，让调用方能够重试。

#### 5. `已完成问答` 第 4 周客户端幂等键需要解决本方案的哪些限制？

它需要识别内容相同或不同但属于同一次业务请求的重试，跨越 10 秒窗口和应用实例持久化处理状态，保存首次请求结果并向重试返回一致响应，还要处理“数据库已成功但客户端未收到响应”等不确定状态。单纯的内容指纹无法表达调用方身份和业务意图，也不能长期保存结果。

### 掌握标准

能够说明短窗口防重的能力和边界，解释指纹、token、TTL、MySQL 保存及失败释放的顺序，并明确 Redis 故障时选择可用性意味着接受什么风险。

- Redis 停止、恢复和客户端重连的实验方法。

### 自测题与参考答案

#### 1. `已完成` Redis 重启后缓存全丢，为什么业务仍应正确？

Redis 只保存可从 MySQL 重建的派生数据，不是事实数据源。缓存丢失后第一次读取可能变慢，但应回源 MySQL 并重新回填；权限也应重新查询关系表。工单防重窗口可能丢失并允许重复，这是已知降级限制，但已成功创建的工单仍保存在 MySQL。若 Redis 丢失会让已有文档永久消失，说明架构错误地把缓存当成数据库。

#### 2. `已完成` `maxmemory-policy` 如何影响只有部分 Key 带 TTL 的实例？

`volatile-*` 策略只淘汰设置了过期时间的 Key，无 TTL Key 会持续占用内存；当带 TTL 的候选不足时，写入仍可能失败。`allkeys-*` 可以从所有 Key 中淘汰，更适合全部数据都可丢弃的纯缓存实例。混合持久数据和缓存数据会让策略选择复杂，因此更稳妥的方向是分离不同用途，并确保缓存 Key 明确设置 TTL。

#### 3. `已完成` 如何客观证明第二次查询命中缓存，而不是“感觉更快”？

可以使用计数 Repository 断言第一次查询调用 MySQL 一次、第二次调用数仍为一次；同时检查业务命中计数增加、Redis 中存在对应版本化 Key 及合理 TTL。真实环境还可结合 SQL 日志或受控指标。单次响应时间受 JVM 预热、网络和数据库状态影响，不能仅凭“第二次更快”证明命中。

#### 4. `已完成` Redis 恢复后客户端是否自动恢复，应该用什么实验验证而不是猜测？

先在应用运行时完成一次正常缓存访问，再停止 Redis，调用同一接口并确认快速回退 MySQL且 HTTP 语义不变；随后恢复 Redis但不重启应用，再次调用并观察是否能够写入、命中缓存以及错误计数是否停止增长。只有这条停止—失败—恢复—再访问链路成功，才能证明当前 Lettuce 与连接配置具有所需恢复行为。

#### 5. `已完成` 本周方案中哪些是最终设计，哪些只是单体学习阶段的过渡方案？

长期保留的原则包括：MySQL 是事实数据源、缓存位于 Controller 之外、Service 面向明确缓存端口、cache-aside、提交后失效、有限超时、故障降级、Key 版本和不泄露敏感内容。

阶段性实现包括：进程内命中率计数、单实例本地 Docker Redis、固定 10 秒内容指纹防重、简单短锁、没有认证保护的内部权限读取，以及手工运行的故障演练。后续阶段可能把指标迁移到 Actuator/Prometheus，把防重升级为持久化幂等记录，并补充认证、限流和多实例验证，但不能因此否定本周学习边界。
