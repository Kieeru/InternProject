## 已完成内容

- 新增 `UserPermissionRepository.findPermissionCodesByUserId(Long)`，以 `Optional.empty()` 表示用户不存在，以 `Optional.of(emptyList())` 表示用户存在但没有权限。
- MyBatis 从未删除用户出发 LEFT JOIN `user_roles`、未删除角色、`role_permissions` 和未删除权限；多角色的重复权限在 Repository 中使用 `TreeSet` 去重并按权限码稳定排序。
- 新增内部 `UserPermissionService`。缓存 HIT（包括空数组）直接返回；MISS 或 UNAVAILABLE 回源 MySQL；不存在用户沿用中文 `ResourceNotFoundException`；未开放权限 Controller。
- 新增 `UserPermissionCache`、NoOp 和 Redis 实现，复用 `CacheStore`、`CacheKeyFactory`、`CacheTtlPolicy`、`RedisCacheProperties`、Jackson 和 `CacheMetricsRecorder`。
- 权限缓存 Key 为 `${prefix}:user-permissions:v1:{userId}`，值为去重且稳定排序的 JSON 字符串数组，TTL 为 5 分钟加 0～60 秒抖动；空数组 `[]` 可命中并记为 `negativeHit`。
- Redis 权限缓存严格校验 JSON 根节点为数组、每个元素为字符串且集合已去重排序；语法错误、JSON `null`、非字符串元素、重复或乱序数组都会精确删除对应 Key 并按 UNAVAILABLE 回源 MySQL。删除损坏值失败也不改变降级语义。
- 提供并测试显式 `evict(userId)`，删除不存在 Key 视为幂等成功，Redis 删除失败返回 `false` 并记录错误；第 6 周角色关系写入应在数据库事务提交后调用该边界。
- 新增 `TicketDuplicateGuard`、NoOp 与 Redis 实现。开启 Redis 时以标题和描述的无歧义长度前缀 UTF-8 编码计算 SHA-256，写入 `${prefix}:ticket-dedupe:v1:{sha256}`；值为每次获取生成的 UUID token，TTL 固定 10 秒。
- `TicketService.createTicket` 在写 MySQL 前执行原子 `SET NX`：首次获取继续保存；重复提交抛出中文 `DuplicateSubmissionException`，由全局异常处理映射为 HTTP 409 / `DUPLICATE_SUBMISSION`；Redis 不可用时 fail-open 并记录错误。
- MySQL 保存成功后防重 Key 保留至 TTL 自然到期；保存失败时以 Lua 原子比较 token 后只删除自己的 Key，释放失败不覆盖原数据库异常并记录防重错误。
- 未修改既有工单状态流转、分页和 `SELECT ... FOR UPDATE` 行锁，不引入公开新 Controller、认证或完整幂等设施。

## 关键决定和剩余限制

- MySQL 继续是权限关系的事实来源；Redis 只位于 Service 与缓存适配器边界。
- 用户不存在不能与现有用户空权限混淆；因此 Repository 使用 `Optional<List<String>>`，缓存只保存已确认存在用户的权限数组。
- 权限 TTL 比文档短，但仍只是兜底；未来角色关系更新必须在事务提交后精确失效。本周没有角色写接口，因此不提前实现事务事件。
- 未开放“查询任意用户权限”的 HTTP API，因为当前尚无登录、认证和鉴权，公开该能力会扩大权限信息暴露面。
- 独立代码审查的 Critical 和 Important 问题均已清零；提出的测试覆盖建议已补充。
- 用户完成五道学习检查。复盘澄清了稳定排序的主要价值是生成确定的缓存 JSON，而不只是便于查找；用户能够说明用户不存在与空权限的业务语义、权限短 TTL、事务提交后失效，以及缺少授权时公开接口造成的权限枚举风险。
- 工单防重采用 fail-open，因为 Redis 只是辅助防重设施，MySQL 工单创建可用性优先；代价是 Redis 故障期间可能创建重复工单。
- 10 秒内容指纹仅表达短窗口内“相同内容”，不保存首次处理状态或响应，不覆盖跨窗口重试，也无法表达客户端业务意图，因此不能称为完整幂等；第 4 周再引入客户端幂等键和持久化结果记录。
- Redis 继续只位于 Service 和缓存适配器边界，MySQL 是工单事实来源；防重区域的内部错误计数不扩展当前公开缓存统计 DTO，避免无计划的 API 字段变化。
